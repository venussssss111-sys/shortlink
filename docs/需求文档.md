# 短链接服务 · 需求文档

> 版本 v1.0 ｜ 作者：（你自己的名字） ｜ 日期：2026-10

## 1. 一句话描述

把长链接压缩成 `https://s.cn/aB3xK9` 这样的短链，用户点击时 302 跳回原地址，同时记录谁在什么时候、从哪里点的。

## 2. 背景：为什么需要它

| 场景 | 痛点 | 短链解决什么 |
|---|---|---|
| 短信营销 | 一条短信 70 字符，长链接能占 200 字符，按条计费 | 链接压到 20 字符，成本降一半 |
| 海报二维码 | 链接太长二维码密度高、难扫 | 短链二维码更清晰 |
| 渠道投放 | 不知道哪个渠道带来的点击 | 每个渠道一个短链，按 code 统计 |
| 数据归属 | 用第三方短链，点击数据在别人手里 | 数据自己存、自己算 |

**核心矛盾**：跳转链路必须极快（用户不能等），统计又必须准确（运营要看数）。整个技术设计都围绕这个矛盾展开。

## 3. 用户与角色

| 角色 | 做什么 |
|---|---|
| 普通用户 / 访客 | 点击短链、被跳转 |
| 运营 / 市场 | 创建短链、看点击数据、按渠道分组 |
| 开发者 | 通过 OpenAPI 批量生成短链 |
| 管理员 | 禁用恶意短链、清理过期数据 |

## 4. 核心概念

- **短码（code）**：短链里那串字符，如 `aB3xK9`
- **原始链接（origin_url）**：跳转目标
- **跳转（redirect）**：302 响应 + Location 头
- **PV**：访问次数，点一次算一次
- **UV**：独立访客数，同一个人同一天算一次

## 7. 三条核心链路

### 7.1 生成

```
校验 URL → 决定短码（自定义 / 随机） → 插入（唯一索引兜冲突，最多重试 3 次）
        → 返回 shortUrl
```

短码两种方案，必须能讲出取舍：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 自增 ID + Base62 | 绝对不冲突、短 | **可枚举**，暴露业务量，能被爬 |
| 随机 6 位 Base62 | 不可枚举 | 有碰撞概率，靠唯一索引 + 重试兜底 |

**本项目选随机**：62⁶ ≈ 568 亿，碰撞概率可忽略；不愿暴露业务量是主因。

### 7.2 跳转（最关键）

```
GET /{code}
 ├─ 布隆过滤器说"一定不存在" → 404（挡掉绝大多数无效请求，不打库）
 ├─ 查 Redis ──命中──→ 校验状态/过期 → 302
 └─ 未命中 → 查 MySQL → 回填缓存（空值也缓存，TTL 60s）→ 302
                                    └→ 异步丢一条访问记录（绝不阻塞跳转）
```

**必须 302，不能 301。** 301 是永久重定向，浏览器会缓存，第二次点击根本不经过服务器，统计全丢。

响应头必须带 `Cache-Control: no-store`，防止中间层缓存导致统计丢失。

### 7.3 统计

```
访问日志（异步落库）
   → 定时聚合（每分钟/每小时）→ link_stats (code, stat_date, pv, uv)
   → 看板查询汇总表
UV：Redis HyperLogLog，key = uv:{code}:{yyyyMMdd}
```

## 8. 数据模型

```
short_link       短链主表
  id, code(唯一), origin_url, expire_time, status, create_time, update_time

access_log       访问原始日志（量大，按天归档）
  id, code, access_time, ip, user_agent, referer

link_stats       按天汇总（看板只查这张表）
  code, stat_date, pv, uv
```

**注意 `code` 字段必须用 `utf8mb4_bin` 排序规则。** MySQL 默认 `utf8mb4_0900_ai_ci` 不区分大小写，`aB3` 和 `Ab3` 会被当成同一个，唯一索引直接冲突。

## 9. 已知坑清单（面试可讲）

1. **排序规则大小写**：见上，必须 `utf8mb4_bin`
2. **统计不能同步写**：跳转链路多一次 DB 写，QPS 掉一半
3. **302 要带 `no-store`**：否则被缓存，统计丢失
4. **开放重定向漏洞**：只允许 `http/https`，拒绝 `javascript:` / `data:` / `file:`
5. **URL 长度**：`VARCHAR(2048)`，别用 TEXT 建索引
6. **IP 字段留 45 位**（IPv6 最长 45 字符）
7. **过期数据清理**：定时任务扫 `expire_time < now`，否则表无限增长
8. **短码别用自增 ID 直出**：可枚举、可被爬
9. **重试风暴**：失败重试要加随机退避
10. **时区**：统计按天必须统一时区（本项目统一 Asia/Shanghai）

## 10. 不做什么（范围边界）

- 不做用户体系与多租户权限（v4 只做单一登录）
- 不做分库分表（只讲思路，不实现）
- 不做 A/B 测试、渠道归因
- 不做短链内容审核（只做域名黑名单）
- 不做前端 SSR / 复杂动效

## 11. 验收标准（做完怎么算成功）

1. 浏览器访问短链能 302 跳转，响应头有 `Cache-Control: no-store`
2. 不存在的短码返回 404，且**没有打到数据库**（看 SQL 日志）
3. 压测报告能给出 v1（无缓存）和 v2（有缓存）的 QPS / p99 对比
4. 看板能显示真实 PV/UV 曲线
5. 一条 `docker compose up -d` 能起全套
6. 你能不看书讲清：为什么 302 不用 301、为什么选随机短码、布隆过滤器怎么防穿透、UV 为什么用 HyperLogLog
