### 2026-10-21 数据库排序规则导致短码冲突
- 现象：插入 `aB3xK9` 后，再插入 `Ab3xK9` 报唯一键冲突。
- 原因：MySQL 默认 `utf8mb4_0900_ai_ci` 不区分大小写。
- 怎么查出来的：`SHOW FULL COLUMNS FROM short_link;` 看 Collation 列。
- 怎么解决的：建库和表都指定 `COLLATE utf8mb4_bin`。
- 还能怎么解：字段级指定 `code VARCHAR(16) COLLATE utf8mb4_bin`。

### 2026-10-25 加速重建时，把「空值缓存」写错位置，导致存在的链接 404
- 现象：把查缓存不命中后的「查库」逻辑抽成 `rebuildWithSingleFlight` 之后，
  **任何一次缓存未命中都会返回 404**，明明库里有这个码。
- 原因：`getByCode` 的漏命中分支里保留了一行旧代码 `writeEmptyCache(code)`，
  它先往 Redis 写了空值，然后才进锁做双检；双检读到的正是刚写进去的空值 → 直接返回 null。
  **空值缓存的语义是「库里也没有」，而不是「缓存里没有」。**
- 怎么查出来的：删掉 `link:V0001` 再请求 `/V0001`，HTTP 404；紧接着 `redis-cli get link:V0001`
  看到值是空串、TTL 30 秒 —— 说明是我们自己写进去的。
- 怎么解决的：删掉那一行，漏命中分支只反回 `rebuildWithSingleFlight(code)`。
- 还能怎么解：让 `writeEmptyCache` 只接受「经过数据库确认不存在」的调用点，
  比如把它合并进 `rebuildWithSingleFlight` 内部（现在就是这么做的），从结构上杜绝误用。

### 2026-10-30 `set(key, value, ttl)` 被解析成 SETRANGE
- 现象：写缓存后 `TTL` 一直是 `-1`（永不过期），`STRLEN` 是 3865 而不是 163。
- 原因：`StringRedisTemplate` 有 `set(K key, V value, long offset)` 这个重载，
  传 `Duration` 时被拆箱成 `long`，于是执行的是 **SETRANGE**（从第 N 个位置开始写），
  前面补了一堆 `\0`，而且不设过期时间。
- 怎么查出来的：`redis-cli ttl` = -1，`redis-cli strlen` = 3865；
  反序列化失败 → catch 里删 key → 看着"缓存没生效"，其实是写坏了。
- 怎么解决的：参数必须显式写 `Duration.ofSeconds(n)`，编译器选到 `set(K,V,Duration)`。
- 还能怎么解：编译期就防住——用 `opsForValue().set(...)` 时别缩写，写全限定重载。

### 2026-10-30 改完代码没重启，测的是旧逻辑
- 现象：fail-open 已经改好，Redis 停掉后请求还是 500。
- 原因：旧的 `java` 进程还在跑（占用 8080），新进程起不来，
  但我只看到 `mvn` 那一行 "Port 8080 was already in use" 就往下走了。
- 怎么查出来的：`netstat -ano | findstr :8080` 拿到 PID → `taskkill //F //PID` → 重启才生效。
- 怎么解决的：改完先确认「跑的是新进程」——看启动日志首行的时间戳和 PID。
- 还能怎么解：把 `Port already in use` 当致命错误处理，脚本里 grep 到就退出。

### 2026-10-30 令牌桶的 rate 写成 int，永远不补票
- 现象：桶空了以后再也不恢复，429 之后一直是 429。
- 原因：配置是 `0.2 张/秒`，用 `int` 接就变成 0，`tokens += elapsed * 0` 恒为 0。
- 怎么查出来的：`redis-cli hgetall rl:ip:auth:127.0.0.1` 看到 `tokens` 一直是 0、`ts` 在变。
- 怎么解决的：`rate` 用 `double`；`ttl` 也要 ≥ `capacity / rate`，否则桶没补满就被删了。

### 2026-10-30 JWT payload 用 String.format 拼 JSON
- 现象：用户名里带一个 `"` 就能让 payload 变成非法 JSON，甚至塞进额外字段。
- 原因：`String.format("{\"name\":\"%s\"}", username)` 没有任何转义。
- 怎么解决的：改成 Jackson 序列化 `LinkedHashMap`，转义和格式都由库负责。
- 教训：**只要涉及「把变量拼进结构化文本」，就别手写拼接**（JSON、SQL、HTML 都是同一个坑）。

### 2026-10-30 nginx 反代 502：`no resolver defined to resolve backend`
- 现象：容器全部 healthy，但所有 `/api/**` 和短码跳转都 502，首页（静态文件）却正常。
- 原因：`proxy_pass` 里用了变量（`set $backend http://backend:8080; proxy_pass $backend;`）。
  用变量时 nginx **不在启动时解析域名**，而是每个请求现场解析，此时必须指定 DNS 服务器，
  否则不认识 Docker 里的服务名 `backend`。
- 怎么查出来的：`docker logs shortlink-web` 直接写着 `no resolver defined to resolve backend`。
- 怎么解决的：加 `resolver 127.0.0.11 valid=10s ipv6=off;`（127.0.0.11 是 Docker 内置 DNS）。
- 为什么不用写死 IP：容器重建后 IP 会变，写死就 502 了；`valid=10s` 让 DNS 结果最多缓存 10 秒。

### 2026-10-30 BuildKit 构建卡在 maven 依赖下载
- 现象：`docker compose build` 停在 `mvn dependency:resolve` 半小时不动，没有任何输出。
- 原因：BuildKit 的构建步骤没法 exec 进去看，`-ntp` 又把下载进度藏了，只能看着干等；
  实测容器到 Maven Central 只有约 250 KB/s，再叠加 BuildKit 的解析开销很难判断是慢还是卡。
- 怎么查出来的：换成经典构建器（`DOCKER_BUILDKIT=0 docker build ... > build.log`），
  构建步骤会以普通容器出现，`docker exec` 进 `du -sh /root/.m2` 能直接看到依赖在长。
- 怎么解决的：用经典构建器 + 把日志写到文件，`du` 采样确认在增长后耐心等（首次约 45 分钟）。
- 教训：**构建慢和构建卡住，看起来一模一样**。要么留可见的输出，要么留可测量的指标。

## 2026-10-30 · nginx 反代没开 keepalive，500 并发腰斩

- 现象：容器化后 500 并发只跑到 6,237 QPS，而且越跑越低（8,957 → 5,008），p99 234ms。
- 怎么查出来的：`docker stats` 看 nginx CPU 1166%（16 核吃掉 11.6 核），backend 只有 156%；
  再去后端容器数 TIME_WAIT —— **14,248 条**。说明 nginx 每个请求都在新建 TCP。
- 原因：`proxy_pass` 用变量 + `upstream` 没写 `keepalive` 时，nginx 不复用后端连接。
- 怎么解决的：upstream 加 `keepalive 128; keepalive_requests 10000;`，
  location 加 `proxy_http_version 1.1; proxy_set_header Connection "";`（这两行是前提）。
- 结果：**15,688 QPS（2.5×），p99 62ms，吞吐稳定**。
- 教训：**反代的默认行为是「每次新建连接」**。压测前先看 TIME_WAIT，比看 QPS 有用。

## 2026-10-30 · nginx 正则里的 {} 不加引号，配置直接起不来

- 现象：`nginx: [emerg] unknown directive "4,10}$"`，容器无限重启，`docker compose ps` 一直 Restarting。
- 原因：nginx 把正则里的 `{` 当成「配置块开始」。`location ~ ^/[A-Za-z0-9]{4,10}$` 会被切断。
- 解决：`location ~ "^/[A-Za-z0-9]{4,10}$" {` —— **正则里带 `{}` 或 `;` 一律加引号**。
- 教训：nginx 配置改完先在镜像里 `nginx -t` 一把，别等容器起来才发现：
  `docker run --rm --entrypoint nginx <镜像> -t`

## 2026-10-30 · curl 登录 200，浏览器登录 403

- 现象：部署到 8088 后点登录一直 403，但 `curl -X POST .../api/auth/login` 返回 200。
  nginx 日志里能直接看出来：浏览器那几条是 `POST /api/auth/login" 403 31`，curl 那条是 `200 463`。
- 关键因果：**浏览器发 POST 一定带 `Origin` 头，同源也带**；curl 默认不带。
  Spring 只要看到 Origin 就走 CORS 校验，不在白名单直接返回 403 `Invalid CORS request`。
- 为什么开发时没事：前端跑在 5173，白名单里正好是 `http://localhost:5173`；部署后 origin 变成 8088。
- 怎么一条命令复现：
  ```bash
  curl -i -X POST http://localhost:8088/api/auth/login     -H 'Content-Type: application/json' -H 'Origin: http://localhost:9999'     -d '{"username":"admin","password":"123456"}'
  # HTTP/1.1 403 + 响应体 20 字节：Invalid CORS request
  ```
- 解决：白名单改成可配置项 `shortlink.cors.allowed-origins`（默认 5173 + 8088），
  compose 里用 `SHORTLINK_CORS_ALLOWED_ORIGINS` 注入，上线换域名只改一处。
- 教训：**同源不等于没有 CORS 校验**。只要请求带 Origin，Spring 就会校验它。

## 2026-10-30 · 越权：任何登录用户都能停用、删除别人的短链

- 现象：v1~v6 只有「认证」（你是谁），没有「授权」（你能动什么）。
  注册一个账号，就能在自己的列表里看到全部短链，还能把 admin 的码停用、删除。
  这是典型的 **IDOR（Insecure Direct Object Reference，越权访问）**。
- 根因：`short_link` 表没有「主人」这一列，所有查询都是 `WHERE code = ?`，
  谁登录都能查到、改到。
- 怎么修的（四层一起改，缺一层都会漏）：
  1. 数据：`short_link.user_id` + `idx_user_id`；`user.is_admin`；
  2. 身份：`is_admin` 编进 JWT（`adm` claim），避免每个请求查一次库；
  3. 服务：创建时写入 `user_id`；列表按 `user_id` 过滤；改/删/详情走 `getOwnedByCode()`；
  4. 统计：排行榜、来源、设备、总览都按 `user_id` 过滤（JOIN `short_link`）。
- 一个刻意的选择：**越权一律返回 404「短链接不存在」，不返回 403「无权限」**。
  因为 403 等于确认「这个码真实存在」，别人拿 403 和 404 的差异就能把全站短码枚举出来。
- 验证：新账号列表 0 条；对其码 PATCH/DELETE/详情全 404；公开跳转仍 302；管理员旁路正常。
